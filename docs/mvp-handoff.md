## Important implementation boundaries

AI Coder is the general-purpose generation system. Music Playlist Mixer is its target generation task and acceptance case. Keep these responsibilities separate:

| Item | Ownership |
| --- | --- |
| Agent orchestration, provider calls, MCP, test execution, recovery and downloads | AI Coder implementation |
| Playlist requirements, sample songs and independent expected results | Generation input and evaluation material; these may be versioned separately from runtime code for reproducible evaluation |
| Playlist UI, genre/mood filtering, ordering, saving and exporting | Application code and tests generated by agents into the selected workspace |

Do not hardcode Playlist Mixer algorithms, song catalogs, domain-specific routing or canned application output into AI Coder's runtime or general agent prompts. Improvements discovered through this case should address a general generation capability and be verified at the existing shared boundary.

```text
UI chat → Coordinator → RunService / scheduler → LangGraph
  → Planner → environment preparation
  → [Tester → Red checks → diagnosis → Coder → Green checks / repair]
  → Architect acceptance → Coordinator report → completed + ZIP

Model calls: LLMGateway.complete → selected adapter → provider
Worker file access: role-scoped MCP tools
Test execution: graph → shared check service
```

- LangGraph/storage own task handoffs. The old MCP `getTask`/`submitResult` workflow is no longer the production path. Do not add another AI client or orchestration framework.
- Tester reads tests and `package.json`, writes tests, and cannot read application source. Coder writes implementation files; environment-repair Coder can write only `package.json`.
- Provider interruptions preserve `continuation.resume_node`. A resumed step retains earlier graph progress but not its in-flight model conversation. It must inspect partially written files. Old continuations without a node retain the planning-based behavior; active runs interrupted by shutdown are marked failed.
- Missing specified implementation modules go to Coder. Syntax attribution uses bounded `node --check` to distinguish broken application code from broken tests. Other failures still need diagnosis.
- Environment repair repeats the affected Red/Green check. Host configuration/network failures pause instead of repeatedly rewriting the manifest.
- Limits are per agent step: 10 model calls, 12 tool calls and 3 consecutive tool errors. The default shared repair budget is 3. There is no run-wide token-budget enforcement or automatic cross-model failover.
- A run retains its selected provider. Model selection comes from the adapter configuration and can change for subsequent calls. The UI offers Groq GPT-OSS 120B/20B; backend configuration of another model does not add a UI option.

Start with [backend setup](../backend/README.md) and [frontend setup](../frontend/README.md). Install dependencies as documented there. The full flow needs Python 3.11+, Node 22.13+ for generated checks, frontend packages and Chrome.

From the repository root:

```bash
(cd backend && .venv/bin/python -m pytest)
backend/e2e/run.sh chat-run
```

The cancellation test requires `ps`; the browser script requires free ports 18081 and 15174 plus Chrome. A scripted test pass does not establish real Groq generation quality.

## Remaining work, in order

### 1. Freeze the Playlist Mixer generation input

The assignment description in [project requirements](project-requirements.md) is broad. The PR does not yet contain a finalized, checkable Playlist Mixer specification or an agent-generated, accepted Playlist Mixer release.

Prepare one reviewed task description and a small deterministic song fixture as generation input, not as AI Coder application features. Confirm the scope with the team/TA. The following describes the application agents should generate; it is a proposed minimal scope, not an already approved specification:

| Feature | Decisions to write down | Acceptance checks |
| --- | --- | --- |
| Catalog and selection | Canonical track fields, genre selection, mood mapping and desired count | Expected eligible songs for known inputs; defined errors for invalid input or too few candidates |
| Generation | Unique track IDs, genre coverage and deterministic ordering or an explicit seed | Correct count and constraints; no duplicates; reproducible fixture results |
| Smooth transitions | Measurable rule, for example adjacent BPM difference ≤ 15; behavior when no valid playlist can be made | Check every adjacent pair; impossible inputs return the agreed failure instead of an invalid playlist |
| Save/export and UI | Local named-playlist storage; JSON and/or CSV schema and order | Reload preserves saved contents/order; export matches the displayed playlist; actual browser controls work |

Include both feasible and infeasible fixtures. Resolve the exact mood/genre rules, tie-breaking and export fields before asking agents to implement them. A BPM ordering rule is a proxy for smooth transitions, not audio crossfade. Keep Spotify/OAuth, streaming, accounts and audio processing outside the proposal unless required by the agreed assignment scope.

**Deliverable:** reviewed generation input, sample data and an independent acceptance checklist. They may be stored as documentation or evaluation assets for repeatability; they must not be imported into the AI Coder runtime to supply the target application's behavior. The agents should generate the Playlist Mixer implementation and its executable tests. Keep the generated feature plan cohesive; test authorship belongs to each feature rather than a separate product feature.

Shell overrides take priority over `.env.local`, then `.env`, then defaults. Backend env loading belongs to its development entry point. Browser-persisted model selection may reapply after restart; panel-added keys last only for the backend process.

Start with `./dev.sh`, create a fresh workspace in the UI, select the intended provider/model and submit a small request such as the documented adder example in [the workflow guide](coordinator-tdd.md). Check tool calls, real tests, completion and ZIP download. A Todo is useful if investigating DOM/persistence problems, but completing another unrelated app is not an MVP deliverable.

Set an explicit evaluation budget for the team's available quota; no reliable Playlist Mixer token-cost measurement exists yet. At 429, distinguish temporary rate exhaustion, daily exhaustion and a request larger than the per-minute cap. Use the receiving account's actual response/limits. Switching models is a manual diagnostic option, not a guarantee of fresh quota. Avoid repeating an unchanged request that cannot fit.

### 3. Generate and verify the agreed Playlist Mixer

Submit the frozen input from step 1 through the actual AI Coder UI with MSW off. Let the agents write application code and tests through MCP. Preserve the same workspace and resume blocked work instead of restarting the entire task after each provider interruption.

Record each failure before changing anything. Check `events.jsonl`, the exact check output and model call metadata. If generation infrastructure is defective, fix the responsible shared boundary and add a meaningful general regression test. If generated Playlist Mixer behavior is defective, return the evidence to the existing agent repair flow. Do not move the target application's implementation into AI Coder to make the demo pass, increase retries indiscriminately or rewrite the whole workflow as a default response.

Verify the generated application independently of its own tests: genre/mood/count rules, every transition, invalid/infeasible inputs, save/reload and export contents. Exercise actual browser controls and inspect actual downloaded data. Architect approval or Green alone does not establish business coverage.

If generated code is manually repaired for diagnosis, record the intervention and rerun generation/validation as appropriate. Do not present a manually completed artifact as autonomous generation.

## Records created on the receiving machine

The backend creates these paths during that developer's own runs; they are not pre-existing artifacts supplied by Git:

```text
workspaces/<workspaceId>/project/                 # Current generated app and tests
workspaces/<workspaceId>/runs/<runId>/run.json     # Status and continuation
                                      tasks.json
                                      checks.json
                                      events.jsonl
                                      usage.json
                                      artifacts/ # Completed ZIP
backend/records/llm.jsonl                        # Shared model-call metadata
backend/records/chat.jsonl                       # HTTP chat metadata
```

Paths can be overridden through backend configuration. Correlate records by workspace/run/call IDs. Shared diagnostics exclude keys and prompt/reply contents. Groq limit metadata is recorded when provided. Unknown provider usage is not reliable zero usage, and run totals are not an account-wide quota ledger. Export the successful run evidence and artifact to the agreed delivery location rather than depending on ignored runtime folders or browser IndexedDB being present on another machine.
